# ผู้ดูแลระบบอ่านข้ามศูนย์ได้ แต่ทุกการเขียนต้องระบุศูนย์ — บังคับให้แน่นที่สามชั้น

ระบบเป็น multi-tenancy แบบ strict: อ่านข้ามศูนย์ได้เฉพาะผู้ดูแลระบบ และการอ่านแบบไม่ระบุศูนย์แปลว่า "ดูทุกศูนย์" ส่วนการเขียนทุกรายการต้องลงจบที่ศูนย์ใดศูนย์หนึ่งเสมอ ขอบเขตนี้เคยถูกละเมิดเพราะมีสองทางออกจากระบบ: `StaffTimeSlotController` ไม่ได้ใช้ trait กลาง และ service รับพารามิเตอร์ `?int` ที่ทำให้ "ไม่กรองศูนย์" เป็นค่าที่ถูกต้อง จึงตัดสินให้บังคับให้แน่นที่สามชั้น เพื่อไม่ให้พึ่งความตั้งใจของคนเขียนอย่างเดียว

## การบังคับสามชั้น

1. **ชั้น controller** — ทุก endpoint ที่เขียนข้อมูลต้องใช้ trait กลางเพื่อ resolve ศูนย์เป้าหมาย แทนการเขียนเอง
2. **ชั้น service** — method ที่เขียนข้อมูลรับ `int` แบบ non-nullable ทำให้เรียกผิดวิธีเป็น compile error ไม่ใช่ runtime bug
3. **ชั้น schema** — คอลัมน์ศูนย์เป็น `NOT NULL` ปิดการเขียนค่าที่ไม่มีศูนย์จากทุกทางรวมถึงการ import ข้อมูลในอนาคต

## การอ่านข้ามศูนย์ไม่ได้มีทุกกรณี

"อ่านได้ทั้งหมด" เป็น**สิทธิ์** ไม่ใช่ค่าเริ่มต้นของทุก endpoint — ใช้ได้เฉพาะที่การดูทั้งหมดมีความหมาย ส่วนรายการที่ผูกกับศูนย์แบบหนึ่งต่อหนึ่ง (ช่วงเวลาของศูนย์) ให้ผู้ดูแลระบบต้องระบุศูนย์เสมอ เพราะการดูข้ามศูนย์แบบนั้นไม่ได้ให้ข้อมูลที่ตีความได้ แต่เป็นการเทียบกับชื่อศูนย์ที่ต้องไล่ตามไปเอง

## Consequences

- การอ่านแบบข้ามศูนย์ยังทำได้ในที่ที่มีความหมาย และต้องระบุศูนย์เพื่อดูเฉพาะศูนย์ได้ — เป็นพฤติกรรมที่ตั้งใจ ไม่ใช่ช่องโหว่
- ประเภทที่ non-nullable และคอลัมน์ `NOT NULL` อาจดูซ้ำซ้อนกับกฎข้อแรก แต่ตั้งใจให้ไว้ทั้งสองชั้น — การ "ตัดให้เรียบง่าย" เพียงชั้นเดียวคือการถอยกลับไปให้บั๊กเดิมกลับมาได้
- controller ใหม่ที่จำเป็นต้องเขียนเอง (เช่น ผู้ดูแลระบบที่ทำงานกับทุกศูนย์โดยไม่มีสิทธิ์เขียน) ต้องมีเหตุผลที่บันทึกไว้ ไม่ใช่แค่ "ไม่ได้ใช้ trait"
