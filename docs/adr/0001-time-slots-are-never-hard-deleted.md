# ช่วงเวลาไม่ถูกลบออกจากระบบ — ปิดใช้งานแทน

ช่วงเวลาถูกอ้างอิงจากสองทางที่บังคับพฤติกรรมต่างกัน: `appointments` ลบด้วย RESTRICT (ลบไม่ได้ถ้ามีนัดหมายแม้แต่รายการเดียว ไม่ว่าสถานะ) และ `service_time_slot` ลบด้วย CASCADE (ลบ config วันให้บริการหายโดยไม่เตือน) ทำให้การ hard delete ไม่มีทางที่ปลอดภัย — ถ้าปล่อยให้ตัว guard หลุดจะได้ error ดิบจากฐานข้อมูล ถ้าไม่มี guard จะเป็นการลบ config อย่างเงียบงัน และการลบช่วงเวลาที่เคยใช้งานแล้วยังไม่มีทางนำกลับมาได้ เพราะ unique key `(health_center_id, start_time, end_time)` จะไม่ยอมให้สร้างเวลาเดิมซ้ำในศูนย์เดิม จึงตัดสินว่า **ช่วงเวลาไม่มีการลบ — ปิดใช้งานแทน** เป็นทางเดินเดียว

## Considered Options

- **เก็บ guard แบบเดิม + เพิ่มกัน cascade** — ยังคง hard delete ไว้ แต่บั๊กที่ผ่านตัว guard ไปแล้วจะลบ config เงียบ ๆ อยู่ดี
- **ปล่อย cascade แล้วบันทึก audit** — ข้อมูลหายอยู่ดี แต่มีหลักฐาน ซึ่งไม่ได้ทำให้ข้อมูลกลับมา
- **hard delete เฉพาะช่วงที่ยังไม่เคยถูกใช้** — ยังต้องตัดสินเรื่องการสะสมของช่วงที่ปิดแล้ว และยังเปิดทางให้เกิด RESTRICT 500 อยู่

## Consequences

- ช่วงเวลาที่ปิดใช้งานแล้วจะอยู่ในระบบถาวร ไม่มีทางลบ — ต้องยอมรับว่ารายการจะสะสม และหน้าจอจัดการต้องกรองสถานะให้ผู้ใช้เอง
- เมื่อปิดช่วงเวลา วันให้บริการที่ผูกไว้ **ไม่ถูกลบ** และกลับมาใช้ทันทีเมื่อเปิดคืน
- คำสั่งลบถูก**เก็บไว้แต่ไม่ให้ผลสำเร็จ** — ตอบว่าไม่รองรับพร้อมชี้ทางเลือกคือปิดใช้งาน เพื่อให้ client ที่ยังเรียกอยู่เห็นคำแนะนำที่แก้ตามได้ แทนที่จะเจอ `405` หรือ error ที่ไม่มีความหมาย

## ขอบเขต — ยกเว้นเมื่อศูนย์สุขภาพถูกลบ

ข้อตัดสินนี้คุ้มครอง **การลบช่วงเวลาโดยตรง** เท่านั้น ฐานข้อมูลตั้ง `time_slots.health_center_id` เป็น `ON DELETE CASCADE` ไว้ ดังนั้น **ถ้าศูนย์สุขภาพถูกลบ ช่วงเวลาของศูนย์นั้นจะถูกลบตาม** และวันให้บริการใน `service_time_slot` จะหายตามช่วงเวลานั้น

ขอบเขตนี้แคบกว่าที่คิด เพราะ `appointments.time_slot_id` เป็น `RESTRICT` — ถ้าศูนย์สุขภาพมีนัดหมายที่อ้างช่วงเวลาของตนแม้แต่รายการเดียว ฐานข้อมูลจะ**ปฏิเสธการลบศูนย์** ไม่ใช่ลบช่วงเวลาให้ ดังนั้น cascade จะเกิดได้เฉพาะศูนย์ที่ยังไม่เคยมีนัดหมายเท่านั้น และการลบศูนย์ที่มีประวัติจริงจะล้มเหลวทั้งก้อน

ขณะนี้ระบบยัง**ไม่มีคำสั่งลบศูนย์สุขภาพ** (มีแค่เปิด/ปิดรับจอง แก้ไข และดูรายการ) จึงยังไม่มีทางในระบบที่จะเรียก cascade นี้ได้ — เป็นเพียงข้อกำหนดระดับฐานข้อมูลที่กันการลบช่วงเวลาทิ้งจากการแก้ข้อมูลตรง ๆ หากภายหลังเพิ่มคำสั่งลบศูนย์ ต้องตัดสินใจเรื่องนี้ใหม่ว่าจะป้องกันการลบศูนย์ที่มีประวัติอย่างไร เพราะ cascade จะไม่ช่วยในกรณีนั้น
